## 1. Entry points and applicability

Rename (`Shift+F6`, "Rename..." in the Refactor menu, editor/Project view/Structure view context
menus, Search Everywhere) renames the *target element* and every usage. The target is, in the
editor: the element the reference at the caret resolves to, else the named declaration whose name
identifier contains the caret; in trees: the selected node's element. Library and decompiled
elements, and elements of non-project files, cannot be renamed.

| ID | Pri | Requirement | Acceptance |
|---|---|---|---|
| REF-REN-001 | MUST | Handler selection: all registered rename handlers that claim the context are collected, keyed by their title; if exactly one claims it, it runs. If several do, the member in-place handler is dropped from the set; if still several, a modal dialog titled `Select Refactoring` with the label `What would you like to do?` and one radio button per handler title (first preselected, `Up/Down` move between radios) lets the user choose; Cancel aborts. If no special handler claims the context the generic element handler is used. | Caret on a Spring bean name that two handlers rename: the `Select Refactoring` dialog appears. |

## 2. In-place versus dialog

`Editor | General | Refactorings` option `Specify refactoring options: In the editor` (default)
selects in-place mode where available; `In modal dialogs` always uses the dialog.

| ID | Pri | Requirement | Acceptance |
|---|---|---|---|
| REF-REN-010 | MUST | Which in-place kind (Java): **variable in-place** (pure text editing of all linked occurrences inside the file, no usage search, no dialog) for elements whose whole use-scope is a local scope in the same file: local variables, resource variables, for-each/for variables, parameters of lambdas and catch clauses, pattern variables, method parameters (of a non-canonical-constructor, non-record-header method), and labeled statements. **Member in-place** (text edit of the declaration name and the references *in the current file*, then a real rename refactoring runs on Enter) for every other member: classes, methods, fields, enum constants, record components and canonical constructor parameters, Java modules. In-place is not used when the caret file differs from the element's file, for the implicit class, in dumb mode when the element needs a search, and when the context keyword is a Java keyword (caret on `this` or `super`). Otherwise the Rename dialog (REF-REN-020). | Shift+F6 on a local: template in the editor. On a public class declared in another file (caret on a reference): dialog. |
| REF-REN-011 | MUST | Variable in-place session: the name is preselected (setting), occurrences are linked, typing updates them live; on Enter the text is kept and nothing else runs, except that Java also fixes name collisions that the new name creates by qualifying (`this.x`) or reports them (REF-REN-100..102); the undo command is named `Rename: {old}`. The caret ends at the end of the new name. | Case REF-REN-011 case 1. |
| REF-REN-012 | MUST | Member in-place session: same editing experience; the old name's declaration and in-file references are linked. The whole result is one undo step named `Renaming {kind} {name} to {new}` (for example `Renaming class Foo to Bar`). If the user types text that is not a valid identifier the confirmation popup of REF-FRM-052 appears. After the refactoring the caret is restored to the end of the renamed identifier. | Case REF-REN-012 case 1,2. |
| REF-REN-013 | MUST | Name suggestion lookup in in-place rename (and in the dialog's name combo): Java suggestions in this order, with duplicates removed and the current name excluded: (1) for a parameter of a method that overrides or implements another method, the name of the corresponding parameter of the first super method; (2) properly cased variants of the current name (class: capitalized; field/variable: the code style prefix applied; a `static final` field: UPPER_SNAKE variants of the name's trailing word sequences; an UPPER_CASE name of another kind: camelCase words); (3) type- and context-based variable names from the code style (`suggestUniqueVariableName`); (4) for a parameter of a setter-like method the property name. | Rename parameter `a` of `void setName(String a)` in a class implementing an interface method `void setName(String name)`: first suggestion `name`. |
| REF-REN-014 | MUST | Switching to the dialog: pressing the Rename shortcut again while the in-place session is active, or choosing `More options...` in the options popup, or clicking the settings link, cancels the template keeping the *typed text* as the dialog's initial name (first entry of the name combo) and opens the Rename dialog for the same element. | Type `n`, press Shift+F6 again: dialog opens with `n`. |
| REF-REN-015 | MUST | Options popup (see REF-FRM-053): checkboxes `Comments and strings` (always shown for member in-place) and `Text occurrences` (shown only where the element kind supports text search). Changing one writes the same per-kind default as the dialog checkboxes (REF-REN-040), restarts the session with the same typed name, and changes the occurrences linked in comments/strings: while `Comments and strings` is on, occurrences of the name in comments and string literals **of the current file** are also linked and edited live in the template (as additional segments). | Tab, tick `Comments and strings`: occurrences in comments are highlighted and follow the typed name. |

## 10. Conflicts and collisions (Java)

Conflicts shown in the framework dialog (REF-FRM-020). "Unresolvable" collisions are those the
refactoring cannot repair; "resolvable" ones are repaired silently by qualification.

| ID | Pri | Requirement | Acceptance |
|---|---|---|---|
| REF-REN-100 | MUST | Existing element with the target name in the same scope. Method: `Method {sig} is already defined in class {C}` (same erasure: `Method with the same erasure is already defined in class {C}`); a base-class method with the same signature that the renamed method would then override: `Method will override {method description} of the super {class description}` (when exactly one of the two is abstract: `Method will implement {method description} of the super {class description}`; when the base method is final: `Method will override final {method description} of super {class description}`; when the renamed method has lower visibility than the accessible base method: `Method will hide {method description} of the super {class description}`); when the renamed method is private, each subclass method with the same signature is reported with the Java bundle text `conflict.message.method.will.override.method.base.class` (not tabulated). Browse` is shown. | Continue over a conflict: skipped dialog appears. |

## 11. Automatic renamers (related elements)

Checkboxes in the Rename dialog that rename *related* elements. After `Refactor`, for each
selected option with something to rename, a table dialog lets the user review/edit.

| Option text (mnemonic) | Applies to | What is offered |
|---|---|---|
| `Rename inheritors` (I) | Java class/interface | subclasses and implementers whose name contains the old class name |
| `Rename variables` (v) | Java class (not anonymous) | variables, fields, parameters (also lambda parameters when fewer than a threshold of files) of this type or of a collection of this type whose name contains the old class name |
| `Rename tests` (e) | Java class that is not itself a test | test classes in the module and dependent modules whose name contains the old class name |
