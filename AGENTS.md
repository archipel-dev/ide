# Archipel IDE engineering guide

## Non-negotiables

- Keep engine crates independent of `egui`, `eframe`, `winit`, and OS UI APIs.
- Every meaningful user action is a typed command registered in `archipel-ide-command`.
- UI controls dispatch commands; they do not own filesystem or project policy.
- Prefer complete vertical slices with tests over empty crates or decorative controls.
- Never claim parity without reproducible evidence recorded in `docs/parity/`.
- Preserve clean-room boundaries: do not copy JetBrains code, artwork, or branding. IntelliJ
  behavior reaches the code only through the specifications in `docs/specs/`, written by a
  separate specification team; implementers never read JetBrains source. See
  `docs/specs/README.md`.
- No new ad-hoc egui painting in `archipel-ide-ui`: use `archipel-kit` components, parts and
  behaviours; if the kit lacks something, add it there. See `docs/ui-migration.md`.
  `cargo xtask design-lint` fails on new `Color32::from_rgb*`, hex palettes, rounded
  `rect_filled` or `CornerRadius::same` outside the kit; after migrating an area, lower
  the baseline with `cargo xtask design-lint --update`.
- Avoid panics on user-controlled input. Return structured, actionable errors.

## Names

Crates are `archipel-ide-<name>` (lib `archipel_ide_<name>`); `archipel-<name>` without `ide`
is a suite crate from the kit or SDK repository. Environment variables are `ARCHIPEL_*`,
per-project data is `.archipel/`. The old Jetthing names live only in `archipel-ide-compat`
and in the few documented compatibility spots (see `docs/architecture.md`); new code
reads environment variables through `archipel_ide_compat::env_var[_os]` and never spells
the old names.

## Required checks

```bash
cargo fmt --all --check
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo run -p xtask -- parity --check
cargo run -p xtask -- spec-coverage --check
cargo run -p xtask -- design-lint
```

Commit messages and PR titles must be Conventional Commits (`feat`, `fix`, `perf`,
`refactor`, `docs`, `test`, `chore`, `ci`; `!` for breaking); they drive automatic
versioning. See `docs/contributing.md`.

## Platform kernel

New feature state is a service of the platform kernel (`archipel-ide-platform`, see
`docs/architecture/platform-kernel.md`), not a field of `IdeState`. `cargo test -p archipel-ide-core`
fails when `IdeState` grows beyond the baseline in `tests/ide_state_size.rs`; moving fields out
lowers it. Features talk through topics and extension points, and the UI reads through services.
`cargo test -p archipel-ide-ui` fails when `archipel-ide-ui` reads `state.<field>` (tests/no_subsystem_reads.rs);
menus, toolbars, context menus, Find Action and shortcuts ask the action registry for a
`Presentation` computed from a `DataContext` (see "DataContext and actions" in the kernel doc).

## Layering

`archipel-ide -> archipel-ide-ui -> archipel-ide-core -> {platform, command, project, plugins}`, with
`archipel-ide-compat` (the old Jetthing names) at the bottom.
Lower layers must not depend on higher layers. `archipel-ide-tui` (the terminal frontend, started
with `archipel-ide --tui`) is a second frontend next to `archipel-ide-ui`: it asks the core through
commands, actions and accessors and owns no project, document or run state; see `docs/tui.md`.
Language integrations belong behind
plugin/service traits, never inside the platform core: a language is a **language pack**
(`crates/archipel-ide-langpacks`) that registers extensions on the language extension points
at start. Core, daemon and UI read the points and never name a language; see
`docs/architecture/language-packs.md` ("How to add a language pack").


## Parity dashboard

`cargo run -p xtask -- parity --check` validates the parity tables (every row has a
known status, IDs are unique across documents). `docs/parity/dashboard.md` is generated by
`cargo run -p xtask -- parity`; feature PRs should not commit changes to it, so parallel
PRs that add rows do not conflict. It is regenerated on main.

## Behavior scenarios

Behavior is specified by recorded scenarios in `docs/parity/scenarios/`, not by memory
(`cargo run -p xtask -- scenario`; format in its README). A fix for a behavior bug starts with
a scenario that shows it; the expected result is what IntelliJ shows, recorded as text only
(markup, popup items, resulting files, never JetBrains screenshots). The CI job
`Behavior scenarios` runs the corpus without blocking and uploads the report.

## Spec coverage

`cargo run -p xtask -- spec-coverage` parses every requirement of `docs/specs/` and writes
`docs/specs/coverage.md` (totals per spec set and priority, per-file breakdown, missing MUST
items). A requirement is `implemented` when its ID is referenced from code (`// JAVA-IMP-012`)
and from a test, scenario or scene (`plat_psi_051` test names count too), `partial` when only
one of them is, `missing` otherwise. Pre-spec code is credited in `docs/specs/coverage.toml`
with a code path and a test path (both verified); be strict, a wrong `implemented` is worse than
a `missing`. `--check` (CI) fails on unknown or duplicate IDs and on override paths that do not
exist, never on missing coverage. The report is a CI artifact; feature PRs need not commit it.
