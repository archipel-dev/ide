# 09-10. Java inspections catalog, part 10 (language injection, logging, manifest, method naming, nullability, pattern validation, properties files, test frameworks, XML)

Status: specification, clean-room. Written from the IntelliJ IDEA Community sources in our own words. Message
templates, option labels and quick-fix names are quoted from the message bundles (short user-visible strings).
Source paths are cited as `ic: <path>`. No code is reproduced. Inventory: `docs/specs/inventory/inspections-java-10.md`.
Requirement ID prefix: JAVA-ICC. Conventions (columns, priorities, ranges, case format) are those of
`docs/specs/java/09-inspections-catalog-7.md` section 0; framework: `docs/specs/codeinsight/03-inspections.md`.
Executable cases: `docs/specs/java/cases/09-inspections-10.cases.md`.

Sources outside the Java modules: `ic: java/langInjection`, `ic: jvm/jvm-analysis-impl` (logging and test inspections, written for the
shared JVM syntax tree and therefore also active in Kotlin), `ic: java/manifest`, `ic: plugins/java-i18n`.
The logging inspections need a known logging library (SLF4J, Log4j 2, java.util.logging, Commons Logging, akka) on the classpath.

## 10. Open questions

1. `NotNullFieldNotInitialized` and `NullableProblems` build most quick fixes through shared annotation helpers (annotate/remove/replace nullability annotations);
   their menu texts (`Annotate ...`, `Remove ...`) are not in the part of the bundle read here.
2. `InconsistentResourceBundle` has one inspection provider per problem kind; the fixes and messages live in provider classes of the i18n plugin and need a separate read.
3. Logging and test inspections depend on library recognition (SLF4J, Log4j 2, JUnit, TestNG, AssertJ). The executable cases assume the library is on the classpath.
