# 07. Safe Delete and the remaining refactorings

Status: specification. Requirement prefixes `REF-SDL` (Safe Delete) and `REF-OTH` (pull up, push
down, extract interface/superclass, encapsulate fields, convert anonymous to inner, copy, make
static, convert to instance method, invert boolean, type migration, use interface where possible,
inheritance to delegation, rare refactorings). Framework rules are in `01-framework.md`.
Executable cases: `cases/07-safe-delete-and-others.cases.md`.

## 1. Safe Delete

| ID | Pri | Requirement | Acceptance |
|---|---|---|---|
| REF-SDL-001 | MUST | `Safe Delete...` (`Alt+Delete`) deletes the selected element(s) after checking usages. In the editor the target is the element at the caret (name of a class, method, field, parameter, local variable, record component, package); without an editor the selected tree nodes (children of selected parents are dropped). Not applicable: error hint `Cannot perform refactoring.` newline `Safe Delete is not supported in current context`. During indexing: `Safe delete refactoring is not available during the project analysis`. Java availability: classes, methods, fields, parameters of methods, packages, local variables, record components. | Case REF-SDL-001 case 1. |
| REF-SDL-002 | MUST | The `Delete` key (`$Delete`) in the Project and Structure views opens the plain delete confirmation `Delete {elements}?` (elements as `class Foo, method bar()`, directories/files by name) that contains the checkbox `Safe delete (with usage search)` (default on, remembered); when ticked the Safe Delete flow below runs, otherwise plain delete. | Case REF-SDL-002 case 1. |
| REF-SDL-003 | MUST | Safe Delete dialog (title `Safe Delete`): message line `Delete {elements}?`, checkboxes `Search in comments and strings` (default on) and `Search for text occurrences` (default on; only for elements where it applies), (in the delete-confirmation form also `Safe delete (with usage search)` which, when off, disables the other two), buttons OK/`Preview`/Cancel. In dumb mode the dialog adds the warning that no usages will be checked. Settings are the application defaults `Safe delete: comments/non-code`. | Case REF-SDL-003 case 1. |
| REF-SDL-004 | MUST | Flow: usages of all targets are searched (progress `Looking for Usages`; also searches usages of callers for parameters: `Search for Caller Method Usages...`). If **no usage** remains (except usages inside the deleted elements themselves and, optionally, in comments/strings which are not code) the elements are deleted at once, without any dialog, in one command `Deleting {elements}`. If usages exist: the dialog of REF-SDL-005. Non-code usages found in comments, strings, text files are *not* conflicts by themselves: they are listed in the preview only (`Occurrences found in comments, strings and non-code files {n}. Those occurrences will not be changed`) unless the setting makes them reported. | Cases REF-SDL-004 case 1-3. |
| REF-SDL-005 | MUST | Unsafe usages (usages in code): the conflicts dialog of the framework (legacy: title `Problems Detected`; buttons `Continue`, `View Usages`, `Cancel`; the Safe Delete specific texts: the dialog message per element `{0} has {1} usage(s) that is/are not safe to delete.` plus `Of those {0} usage(s) is/are in strings, comments, non-code files or generated code.`; individual messages `Usage of {0} that is not safe to delete.`, `Usage of {0} in string, comment or non-code file that is not safe to delete.`, `Usage of {0} in generated code that is not safe to delete.`). `View Usages` opens a Find tab titled `Safe Delete Conflicts` with the node `Attempting to delete` (targets), `Potentially unsafe to delete references found in code {n}` and `Occurrences found in comments, strings and non-code files`, and the actions `Rerun Safe Delete` (re-checks; button text `Rerun &Safe Delete`) and `Delete Anyway` (command `Delete Anyway`; text `&Delete Anyway`); `Continue` in the dialog deletes ignoring the usages (the references stay and break). | Case REF-SDL-005 case 1. |
| REF-SDL-006 | MUST | Java deletion rules: deleting a **class** deletes it and, if it was the only class and the file name matches, the file; usages in `import` statements, `extends`/`implements` lists are *safe* (the import is removed; a removed `extends` entry is a conflict unless the whole subclass is deleted too); static imports of deleted members are removed. Deleting a **method**: all overriding methods are offered (REF-SDL-007) and `@Override` annotations of the remaining ones are removed when no base remains; calls are unsafe usages; a method implementing an abstract method is a conflict (`{0} implements {1}.` capitalized). Deleting a **field**: assignments (write-only usages) are safe and deleted (`field = x;` statements removed when the right side has no side effects, otherwise only the left part); getters and setters are offered (REF-SDL-008). Deleting a **local variable**: its initializer's side effects are kept as a statement. Deleting a **parameter** (REF-SDL-009). Deleting a **package** deletes its directories. A method reference or lambda target usage gives `Method reference will be converted to lambda expression warning`-style conflict (`Method reference will be converted to a lambda expression`). | Cases REF-SDL-006 case 1-4. |
| REF-SDL-007 | MUST | Overriding methods: when the deleted method is overridden in the project a modal dialog titled `Unused Overriding Methods` shows `There are unused methods that override the methods that are going to be deleted. Choose the unused overriding methods you want to delete as well:` and a checkbox list of the overriders (all ticked) with a source preview; OK deletes the ticked overriders too, Cancel aborts the refactoring. Overriders that are *used* are not listed and become usages (conflicts). | Case REF-SDL-007 case 1. |
| REF-SDL-008 | MUST | Getters and setters of a deleted field: after the dialog a question `Getter and setter methods found for the field {0}. \nDelete them as well?` (one of them: `Getter method found for the field {0}. \nDelete the getter as well?`, `Setter method found for the field {0}. \nDelete the setter as well?`) with `Yes`/`No`; Yes adds them (and their overriders) to the elements to delete, and then their remaining callers are conflicts. | Case REF-SDL-008 case 1. |
| REF-SDL-009 | MUST | Deleting a method **parameter**: unused-in-body parameters are removed from the declaration and from every call (arguments with side effects are kept as statements before the call when they cannot be dropped); a parameter used in the body is a conflict (`{0} is used in method body`) reported as usage of the parameter; for a method in a hierarchy the question `{0} is a part of method hierarchy. Do you want to delete multiple parameters?` (Yes: all overriders/bases, No: only this one, Cancel) is asked first; when callers pass the parameter on to other methods (call hierarchy) the chooser `Select Methods To Propagate Parameter Deletion` opens (tree of callee/caller methods, preview panes `Callee text would be shown here` / `Caller text with highlighted callee would be shown here`) so the user can choose to delete the forwarded parameters too; a usage that is not safe yields `{0} has a call-side usage that is not safe to delete.` A method reference to the method is converted to a lambda with the warning. | Case REF-SDL-009 case 1,2. |
| REF-SDL-010 | SHOULD | Related files: deleting a file with nested related files (project view nesting) asks `Related file found: {0}.<br/>Delete it as well?` (`Related files found: ...<br/>Delete them as well?`) before the delete. Directories: deletion confirmation lists files; `Items to be deleted` is the preview header. | |
| REF-SDL-011 | MUST | Command and undo: `Deleting {elements}` single command; Undo restores all deleted code and files. | Undo a safe delete: all back. |
| REF-SDL-012 | SHOULD | Kotlin Safe Delete: same dialog; Kotlin specifics: deleting a property deletes its accessors and the backing parameter of a primary constructor property (`val` parameter becomes plain parameter only when deleting the property keeps the parameter used), deleting a primary-constructor parameter updates all constructor calls (also named arguments), overriders offered as in Java (dialog `Unused Overriding Methods` text uses `declarations`), the message `{0} implements {1}.` for implemented members, the action text `Safe delete constructor`; deleting a class deletes `expect`/`actual` counterparts only after a question. | Cases REF-SDL-012 case 1,2. |

## 2. Pull Members Up / Push Members Down

| ID | Pri | Requirement | Acceptance |
|---|---|---|---|
| REF-OTH-001 | MUST | `Pull Members Up...`: caret in a class (or selected members); dialog `Pull Members Up` with the label `Pull up members of {Class} to:` and a combo of the direct and indirect superclasses and implemented interfaces in the project (nearest first, `java.lang.Object` and library classes excluded); the table `Members to be pulled up` (columns: checkbox, member with icon and signature, `Make Abstract` checkbox for methods) listing fields, methods, inner classes, `implements` entries (`implements {0}`, `extends {0}` rows for interfaces); the initially ticked members are those selected at invocation; the panel `JavaDoc for abstracts` with `As is` (default), `Copy`, `Move` (enabled when abstract methods are made); `Preview`/`Refactor`. Errors: `Caret should be positioned inside the class to pull members from`, `{0} does not have base classes/interfaces in current project`, `Class {0} does not have base classes or interfaces`, `Interface {0} does not have base interfaces`, `No members selected`. | Cases REF-OTH-001 case 1,2. |
| REF-OTH-002 | MUST | Result: ticked members are moved to the target (fields/methods/inner classes keep their bodies; methods with `Make Abstract` leave a copy with the body removed and an `@Override`-less implementation remains in the original class, i.e. the target gets `abstract` method and the source keeps the implementation); an interface target gets `public`-less method declarations (abstract) or default methods are not generated automatically (abstract declarations only; bodies stay in the implementing class); fields pulled to an interface become `static final` constants only if constant; `implements` entries move to the target's `implements`/`extends`. Required dependencies produce conflicts. Command `Pulling members up from {class}`. | Cases REF-OTH-001 case 1,2. |
| REF-OTH-003 | MUST | Pull up conflicts: `{0} uses {1}, which is not accessible from the superclass`, `{0} uses {1}, which is not moved to the superclass`, `{0} already contains a {1}`, `{0} in superclass would clash with a {2} method from {1}` (`push.up.super.class.signature.conflict`), `{0} uses {1} which won't be accessible from the subclass.`, `Can't make {0} abstract as it won't be accessible from the subclass.`, `Superclass won't be accessible in subclass`, `{0} is {1} and will not be accessible from {2} in the target class.`, `Class {0} not found.`, `required by {interface(s)} {n}` hints in the table. | Case REF-OTH-003 case 1. |
| REF-OTH-010 | MUST | `Push Members Down...`: dialog `Push Members Down` with the label `Push members from {Class} down`, table `Members to Be Pushed Down` (columns: checkbox, member, `Keep abstract` checkbox for abstract/interface methods) and panel `JavaDoc for abstracts` (`As is`, `Copy`, `Move`); the members are pushed to **all direct subclasses**, with `Keep abstract`: the method stays abstract in the superclass and a copy is added to subclasses. Errors: `Caret should be positioned inside the class to push members from`, `Class {0} does not have inheritors`, `Interface {0} does not have inheritors`, `Class {0} does not have inheritors.`, `Final class {0} does not have inheritors.`, `Enum {0} doesn't have constants to inline to.`, `No members selected`, `Unsupported source/target pair detected`. With no subclass: question `Pushing members down will result in them being deleted. Would you like to create a new subclass?` (or `... Would you like to proceed?`). | Case REF-OTH-010 case 1,2. |
| REF-OTH-011 | MUST | Push down conflicts: `{0} is already overridden in {1}. Method will not be pushed down to that class.`, `{0} uses {1}, which is pushed down`, `Pushed members will not be visible from certain call sites`, `Super method call will resolve to another method`, `{0} will inherit unrelated defaults from {1} and {2}`, `Members to be pushed down already exist: {0} already exists in the target class.` Command `Pushing members down`. | |

## 4. Encapsulate Fields

| ID | Pri | Requirement | Acceptance |
|---|---|---|---|
| REF-OTH-030 | MUST | `Encapsulate Fields...` (on a field name, in a class, or selected fields): dialog `Encapsulate Fields` with the table `Fields to Encapsulate` (columns `Field`, `Getter`, `Setter` with checkboxes for generating them; getter/setter names editable), border `Encapsulate` with checkboxes `Get access` and `Set access` (apply the access redirect to usages), `Use accessors even when field is accessible` (default on: `ENCAPSULATE_FIELDS_USE_ACCESSORS_WHEN_ACCESSIBLE`), border `Encapsulated Fields' Visibility` (radios `As is`, `Escalate`... shown as `Private`, `Protected`, `Package local`, `Public` with default `Private`), border `Accessors' Visibility` (default `Public`). Errors: `Encapsulate fields refactoring cannot be applied to interface`, `Class has no fields to encapsulate`, `Nothing found to encapsulate`, `Fields to be refactored should belong to the same class`. | Case REF-OTH-030 case 1. |
| REF-OTH-031 | MUST | Result: for each selected field the missing getter (`getX`, `isX` for `boolean`, prefix/suffix conventions of the code style) and setter (`setX`, none for `final` fields) are generated (existing ones are reused); the field becomes private; every read outside the declaring class (or everywhere with `Use accessors even when field is accessible`) becomes `obj.getX()`; assignments `obj.x = v` become `obj.setX(v)`; compound assignments and `++` become `obj.setX(obj.getX() + v)`; inside the declaring class direct access is kept unless the option says otherwise. Conflicts: `There is already a {0} which would be hidden by generated accessor`, `There is already a {0} which would hide generated accessor for {1}`, `There is already method {0} which differs from getter {1} by return type only` (setter likewise), `Unable to proceed with postfix/prefix expression when it's result type is used`. Command `Encapsulating fields in {0}`. | Case REF-OTH-030 case 1,2. |
